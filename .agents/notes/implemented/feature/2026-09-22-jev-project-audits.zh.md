# Agent Note: JEV project audits are durable evidence runs

Status: implemented

## Problem

只判断一张卡片正文，可以回答需求看起来是否可执行，却无法证明项目交付健康度。规划、实现风险、测试、发布准备度和规范漂移需要不同问题与不同证据。手工重复调用单卡工具也无法保持覆盖率、进度、取消和重启历史。

## Decision

`devflow-jev` 以持久化只读运行的方式负责项目审查。一次审查会快照完整的活动 Devflow 看板，跨阶段抽取卡片，收集由 journal 推导的卡片状态、完整 journal、已登记产物和父子卡摘要，再根据命名 profile 规划适合当前阶段的检查。每种 assessment kind 使用独立的类型化问题。模型答案保留为单项证据；确定性代码负责计算覆盖率、缺失证据、发布阻断、高实现风险、规范缺口和父子卡冲突。

不可变 manifest 固定卡片 revision、证据 digest、rubric 版本和检查标识。每完成一次检查就把状态提交到 `.devflow/judgements/audits/<run-id>/`，同时保存单项 evaluation 和终态报告。Harness job 提供所有者范围内的进度与取消，项目文件则是重启后的权威记录。缺少活动 runner 而遗留为 `running` 的运行转为 `interrupted`；显式恢复只重试未完成或已过期的检查，并只保留证据摘要与 rubric 身份仍匹配的已完成检查；过期检查会明确标为 `stale`。

已登记产物路径是不可信输入。采集范围限制在卡片目录内，拒绝路径穿越、符号链接逃逸、可能携带凭据的文件名、非普通文件和超过字节预算的文件。缺口作为报告证据保留，而不会触发更广泛扫描。审查不会执行仓库命令、创建卡片或移动阶段。

原生 [JEV 审查工作台](2026-09-22-jev-review-workspace.zh.md) 将 Devflow 审查、通用运行和单项评估一起展示。模型工具和会话范围 HTTP 页面操作同一组持久化运行。

## Alternatives considered

**新增 project-audit 包。** 未采用，因为审查规划、证据、evaluation、需求 proposal、持久化、工具和现有面板属于同一个归属 seam。拆包会暴露没有独立消费者的内部协调接口。

**用一次大型模型请求审查整个项目。** 未采用，因为它没有单卡提交点，很快超出证据预算，无法安全恢复，而且一次 provider 失败会丢失全部进度。

**所有审查类型共用一套问题，仅更换标签。** 未采用，因为标签不会改变实际判断内容。发布证据、测试新鲜度、实现风险和规范覆盖需要不同的类型化问题。

**自动移动卡片或创建整改卡。** 未采用，因为审查提供的是建议性证据。检查 finding 后的工作流变更仍由人或 agent 显式执行。

## Consequences

审查可能持续较久并消耗多次 provider 调用，但进度可见，部分结果也能跨重启保留。产物预算可能把较大但有用的文档标记为 oversized；正确处理方式是登记聚焦的报告，而不是静默扩大信任与 token 范围。首版读取已登记的 Devflow 证据，不运行测试，也不扫描任意源码，因此可以识别缺少证明，却不会制造证明。

单元、客户端和真实 Loader/HTTP/jobs 组合测试覆盖独立 rubric、持久化完成、取消与恢复、卡片不变性、finding、所有者隔离和原生面板操作。完整构建与本地安装后的运行验证证明包、浏览器产物、工具和会话范围路由能够共同工作。
