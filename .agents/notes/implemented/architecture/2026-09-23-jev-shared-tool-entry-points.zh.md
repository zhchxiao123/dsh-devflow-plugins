# Agent Note: 工具与审查工作区共用 JEV 入口

Status: implemented

## Problem

按运行类型和动作分别命名工具，迫使调用者在多套生命周期接口之间选择。Devflow 审计还在工具和 HTTP 中分别实现启动逻辑，导致归属校验、绑定失败与重试行为可能不同。浏览器可以查看通用审查，却只能通过工具定义创建它。

## Decision

通用运行插件注册 `jev_run`、`jev_list` 和 `jev_control`。来源适配器通过 `ctx.jevRuns` 注册，通用包不依赖 Devflow。Devflow 提供审计和评估来源，仅注册 `devflow_assess` 和 `devflow_decide_judgement`。专门判断文件风险的 `jev_triage` 与运行生命周期保持独立。

列表项包含 source、id 和原始记录。读取单条记录必须同时指定 source 和 id，避免不同存储中的编号冲突。该接口只能读取评估记录；需求、任务评估与提案决定仍属于 Devflow 适配器。来源不可用或不支持操作时明确报错，注册通过 effect 绑定销毁函数。

Devflow 适配器让工具与 HTTP 共用评估校验、提案决定和审计作业控制。需求与任务评估的字段互斥。启动和恢复要求实时 owner；取消保留 Harness 归属检查。绑定失败会取消刚创建的作业。逐运行串行控制避免同进程并发调用相互覆盖作业绑定。

审查工作区支持通用证据清单、Devflow 审计、新需求评估和已有任务评估。证据清单将用户提供的证据与是非问题编译成工具使用的同一种持久化通用定义。评分、多选和分项证据仍可通过完整定义提交。表单不会采集仓库文件。展示与范围语义见[审查工作区说明](../feature/2026-09-22-jev-review-workspace.md)。

旧工具别名从模型注册表中移除。现有 HTTP 方法作为轻量服务适配器保留，`.jev` 与 `.devflow/judgements` 中的持久化记录保持格式和位置不变。部署需要重新构建并重启本地插件组合。

## Alternatives considered

**保留已注册的别名。** 模型仍需面对大量近似工具，无法得到精简后的接口。

**把 Devflow 分支放进通用引擎。** 这会把领域无关执行与任务卡存储耦合。来源适配器将依赖保留在消费方。

**让浏览器调用模型工具。** HTTP 与工具需要不同的参与者和会话解析；共享领域服务能保留边界并避免重复行为。

## Consequences

调用者必须使用新的工具名称和 source/id 选择器，历史工具调用仍作为历史记录保留。UI 与工具操作同一份持久化数据，无需迁移。来源注册是进程内行为，生命周期串行控制不提供分布式协调保证。实际判断仍需要提供方凭证；注册和路由验证成功并不能证明提供方的判断质量。
