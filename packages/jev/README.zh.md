# 类型化判断服务

`ctx.jev` 定义提供可被代码直接消费的、带校准概率的类型化判断：调用方交出一个 **State** 和一组类型化的 **Question**，拿回带结论和其背后分布的 **Answer**。这里不生成散文，也不解析散文。请加载一个 provider，例如 `@zhchxiao123/dsh-jev-typesafe`；本包是词汇与契约，因此组合里挂的是 provider 而不是这个类。

Question 有三种。**Choice** 从定义好的集合里选出一个选项，并返回每个选项的概率。**Score** 在你描述的有序档位上评级，并返回每一档的概率；档位的下标就是它的分值，所以这些档位本身就是分数的含义。**Noul** 返回某个条件成立的概率——它不带独立的置信度，因为接近 0.5 的取值说的是"是"与"否"几乎等可能，这是关于问题本身的陈述，而不是某种更弱的版本。

一次调用中的所有 question 都针对同一个 State 作答，彼此独立。共享的证据放进 State；只对某一个 question 成立的内容放进该 question 自己的 `instructions`，它既接受散文也接受结构。question 的键是给你的代码寻址用的，不会进入判断，因此每个 question 必须在自己的字段里携带完整含义。

## 契约

`ask(request, signal)` 代表每一个 provider 守住三条保证，好让某个 provider 弄错其中一条时不会悄无声息地错下去。

**答案被限制在被问过的键上。** provider 返回了多余的内容，多余的部分会被丢弃。

**没有作答的 question 保持缺席。** 它永远不会被填成 `null` 或零，因为调用方必须始终能分辨"被判在了档位最低处"和"根本没有被判断"。

**失败抛出 `JevError`，并带上 `code`。** 一个不可用的判断该 fail open 还是 fail closed，是消费方的策略——一个在无法判断时把所有文件都送去评审的分诊工具是安全的，而一个做同样选择的审批消费方则不然。一个吞掉自身失败的传输层，会一次性把这个决定从所有消费方手里拿走。这些 code 把凭据引用缺失、端点不可达、限流拒绝、答案不可解、请求被撤回分开，因为它们需要运维上不同的应对。

`JEV_ABORTED` 是取消，不是判断不可用。消费方必须把它重新抛出，而不是并进 fail-open 分支；一次被撤回的调用如果报出一整套保守结果，看起来就像成功了。

形状上已经无法作答的请求——没有 question、类型未知、Score 没有档位、Choice 没有选项或超过 255 个——会在任何 provider 为它花掉一次调用之前，以 `JEV_INVALID_REQUEST` 被拒。

## 通用运行

`JevRunEngine` 执行一组与业务领域无关的类型化检查。一次运行声明 scope 和 template，每个检查提供自己的 subject、证据摘要和 `JevRequest`。引擎负责进度、取消、部分重试、provider 错误记录和孤立运行恢复；它不知道 Devflow 卡片、GitHub Issue、代码仓库或调度器。

`DurableJevRuns` 通过 `FileJevRunStore` 增加原子文件持久化。调用方自行选择存储根目录，因此仓库适配器、GitHub 适配器和定时自动化可以复用同一套运行生命周期。证据采集和类型化答案解释仍由各适配器负责。

## Configuration

本包没有配置项。端点、模型、凭据引用、超时与重试策略都是 provider 拥有的部署选择，阈值则由每个消费方各自拥有。

## Known limitations

**没有全局判断索引。** 持久运行写在调用方选择的根目录下。跨项目检索应由宿主 UI 或索引适配器提供，而不是由本包决定。

**没有 cordis 事件。** 一个 scope-filtered 事件需要在 harness 生成的 scope 表里有一条路由，而 harness 之外的包无法添加它。消费方改为通过自己的结果来观察判断。如果将来真的出现跨插件的订阅方，未作用域事件这条路仍然可走。

**没有 provider 注册表。** 同一时刻只有一个 provider，靠被挂载完成注册。第二个后端才需要选型规则与歧义错误；现在加上它们只会是个空壳。

**发布的运行期不变量 companion 不带检查。** 三条契约关系全都在一次 `ask()` 的调用栈内成立并在那里断言，因此一个从外部观察的观察者没有任何独立的东西可供比对。
